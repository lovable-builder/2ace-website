1. Setup and maintenance

What keeps the platform running. Never paste secret values into chat or code. They live in Supabase and in a private .env file.

Publishing changes

  • Website and admin pages: pushing to GitHub main deploys to 2ace.pl by itself within about a minute. Hard-refresh (Cmd+Shift+R) to see changes.
  • Database: supabase db push --yes applies new migrations. Do this before testing a new feature.
  • Server functions: supabase functions deploy <names> --use-api --project-ref <project> publishes changed functions.

Before you deploy, run the test suites: cd tests && bash run.sh (once, npm install inside tests/). Every suite must say ok. Server functions have their own tests: deno test supabase/functions/_shared/.

The server functions are admin-api, change-plan, create-checkout, change-request, customer-shipping (customers' own labels), booking and booking-reminders (booked calls), stripe-webhook, request-help, lead and the domain and invoice functions. When a feature stops working after an update, deploy the ones named in the instructions.

Booked calls: first-time setup

  1. Run supabase db push --yes. This creates the booking tables and, when the project allows it, schedules a job every 10 minutes that sends reminders (Supabase pg_cron and pg_net, both free).
  2. Deploy the functions: supabase functions deploy booking booking-reminders admin-api --use-api --project-ref <project>.
  3. Sign in to the admin panel, open Appointments → Booking settings and open each language you want: time zone, who is emailed, opening times. Nothing is bookable until you do.
  4. Book a test call at 2ace.pl/book with your own email. You should get the confirmation with a calendar file, and the team inbox gets the booking. Cancel it from the link in the email.
  5. Look at the top of Appointments: it should say Reminders are running within 10 minutes. If it says they are not, see below.

Emails need RESEND_API_KEY and a verified sender (see the settings table). SITE_URL is used for the links in the emails. The booking page needs no account, so anyone can use it; each email address can hold at most 3 upcoming bookings, and a hidden field catches simple bots.

Fulfilment as you go: switching it on

Customers choose it in the plan builder (Fulfilment as you go, no monthly fee) instead of Fulfilment. For a customer on that plan, buying labels is still closed until you open it, in two steps, so nothing can spend money by accident.

  1. Deploy: supabase db push --yes, then supabase functions deploy customer-shipping admin-api change-plan --use-api --project-ref <project>.
  2. For a test customer: Customers, open the company, Shipping and fulfilment, Edit. Set the mode to Fulfilment as you go (this overrides their plan, for testing), tick May buy labels themselves, check the markup and the limits (labels per day, total not yet invoiced), and save.
  3. Set the secret CUSTOMER_LABELS_ENABLED=true (supabase secrets set CUSTOMER_LABELS_ENABLED=true --project-ref <project>), and keep FURGONETKA_ENV on sandbox for the test. Labels bought in the sandbox are recorded as waived, so a test never bills anyone.
  4. Sign in as the test customer, open an order's Shipping, price a parcel and buy. Then pick and pack the order as staff: the order card shows who bought the label, and a parcel that differs from the declared one is flagged.
Before real customers use it

Every live label creates a charge in the customer's shipping ledger (pending). Automatic invoicing of these charges to Stripe is not built yet, so for now the charges must be added to invoices by hand. Do not set CUSTOMER_LABELS_ENABLED for live customers until you have decided how the charges are invoiced. Also have the shipping fees reviewed in the terms with your accountant (VAT on re-sold carrier services, credit notes).

Pay as you go: billing the usage charges

Customers on Fulfilment as you go and Returns as you go pay no monthly fee for those services. Instead each shipped order writes a handling fee, each return a return fee, and bought labels write label charges into the ledger. When Stripe creates a customer's monthly subscription invoice, the charges are added to it as lines, with a credit line if the month's handling or return fees pass the ceiling per m² (350 and 150 by default). Nothing is charged at the moment of purchase, so a failed card cannot block a plan change.

  1. Deploy: supabase db push --yes, then supabase functions deploy stripe-webhook customer-shipping admin-api change-plan create-checkout --use-api --project-ref <project>.
  2. In the Stripe dashboard (Developers → Webhooks → your endpoint) add three events to the ones already there: invoice.created, invoice.finalized and invoice.voided. Without them the charges are never added to invoices.
  3. Set the prices: Shipping → Handling fee tariff (the shipped values are placeholders for you to replace). Check the ceilings and mark a test customer Live under Customers → Shipping and fulfilment → Edit.
  4. Test in Stripe test mode first: ship an order and receive a return for the test customer, then advance its test subscription to the next cycle (Stripe: Test clocks, or "Advance time"). The new invoice should show the usage lines, and the credit line if the ceiling applied. Then set USAGE_BILLING_ENABLED=true (supabase secrets set USAGE_BILLING_ENABLED=true --project-ref <project>).
  5. Go live per customer: only customers marked Live are billed; everyone else's fees are recorded as test and never invoiced.

Each charge moves through pending (waiting), queued (added to a draft invoice), invoiced (the invoice was finalized) and paid. If an invoice is voided its charges go back to pending and are added to the next one. Asking again for the same invoice never adds a line twice. Only the monthly subscription invoice carries usage: an upgrade invoice or a one-off invoice never does. VAT on the lines follows the invoice's tax settings: check with your accountant that re-sold carrier services and handling fees get the VAT treatment you expect, and that credit lines are acceptable on your invoices.

Before real customers

The tariff prices and the ceilings are yours to set and the terms page describes them: have the wording reviewed. Test one full billing cycle before switching USAGE_BILLING_ENABLED on for live customers. Return labels from a private person's address depend on what Furgonetka allows: try one in the sandbox first.

RESEND_API_KEY, EMAIL_FROMSending emails. The sending domain must be verified in Resend. Suggested sender: 2ACE <hello@2ace.pl>.
LEAD_NOTIFY_TOThe team inbox for contact forms, requests, discrepancies and change requests: hello@2ace.pl.

HOSTINGER_API_TOKEN, HOSTINGER_AUTO_REGISTER, HOSTINGER_MAX_FIRST_YEAR_PLN, HOSTINGER_MONTHLY_CAPOptional automatic domain registration with a price ceiling and monthly limit. Keep it off until you trust the manual queue.
FURGONETKA_ENV, FURGONETKA_CLIENT_ID, FURGONETKA_CLIENT_SECRET, FURGONETKA_USERNAME, FURGONETKA_PASSWORDThe connection to Furgonetka for shipping labels. FURGONETKA_ENV is sandbox while testing and production when live. The Client ID and Secret must belong to that same environment. Keep two-step login off on that Furgonetka account, and use a password that is unique to it. Check it under Shipping → Test connection.
SHIPPING_ENABLEDThe kill switch for buying labels. Labels can only be bought while this is exactly true. Leave it unset until you have tested in the sandbox and topped up the balance. Setting it to anything else switches buying off at once. Getting prices stays available.
SHIPPING_MARKUP_PERCENTWhat we add to the carrier's net price when charging the customer. Default 30 (a label that costs us 10,00 zł net is charged 13,00 zł net, plus VAT). Changing it only affects labels bought afterwards.
SHIPPING_AUTO_LABELAutomatic labels. While this is exactly true, finishing the packing of an order on the scan page buys the cheapest carrier that can take the parcel, with no extra click. It never overrides a limit: a label above the per-label limit, an empty balance, the daily cap, an unconfirmed carrier answer or an order that has the customer's own label all stop it, and the order waits for a person with a clear message. Unset (or anything else) = off. It also needs SHIPPING_ENABLED=true. Test it in the sandbox first.
SHIPPING_MAX_LABEL_PLN, SHIPPING_DAILY_CAP_PLNSpending limits, in złoty with VAT. A single label above SHIPPING_MAX_LABEL_PLN (default 80) needs an admin to confirm it. Once the day's labels (Polish time) would pass SHIPPING_DAILY_CAP_PLN (default 500), buying stops for everyone until the next day or until you raise the limit.
USAGE_BILLING_ENABLEDPuts usage charges (shipping labels, handling fees, return fees, return labels) on the customer's monthly invoice. Exactly true to switch on; anything else leaves the charges waiting in the ledger. Needs the three extra Stripe webhook events below. Leave it off until you have tested one cycle in Stripe test mode.
CUSTOMER_LABELS_ENABLEDThe kill switch for customers buying their own labels (Fulfilment as you go). Customers can only buy while this is exactly true and an admin switched it on for that customer. Leave it unset until you have tested in the sandbox and decided how shipping charges are invoiced.
CUSTOMER_MAX_LABEL_PLN, CUSTOMER_DAILY_CAP_PLNLimits for customer purchases, in złoty with VAT of what we pay. A single label above CUSTOMER_MAX_LABEL_PLN (default 60) is not offered. All customers together may spend CUSTOMER_DAILY_CAP_PLN a day (default 150), and with staff purchases never more than SHIPPING_DAILY_CAP_PLN, so staff can always ship. Customers cannot override any of these.
Per-customer shipping settingsIn Customers, open a customer and look at Shipping and fulfilment. An admin can click Edit to set that customer's own markup (empty = the default SHIPPING_MARKUP_PERCENT), the most unpaid shipping they may have at once, the labels per day, whether they may buy labels themselves (off by default), and a fulfilment mode override used only for testing (normally the mode follows their plan: Fulfilment, or storage only. "Fulfilment as you go", where customers buy their own labels, is not offered in the plan builder yet; the override is how you try it).
SHIPPING_CARRIERSOptional. A comma-separated list of carrier codes to compare, for example inpost,dpd,dhl,gls. The default is InPost, DPD, DHL, GLS, UPS, FedEx, Poczta Polska and ORLEN Paczka.
Database setting auto_putawayIn the table wms_settings. on (the default): good goods from a booked delivery are stored straight into the customer's bin. off: they wait in the receiving area for a put-away, as in the old two-step flow. Change it with the SQL editor: update wms_settings set value = 'off' where key = 'auto_putaway';
Features that are switched off2ACE Market is hidden but not deleted. The page market.html and all its code are still in the repository. To bring it back: set MARKET_ENABLED to true in scripts/features.mjs and in platform.html, remove the market line from .htaccess, uncomment the two MARKET-OFF blocks in index.html, then run node scripts/build-seo.mjs and node scripts/build-news.mjs.
STRIPE_AUTOMATIC_TAXTurn on only after your VAT registration exists in Stripe.
Supabase Auth: Site URL https://2ace.pl, redirect URLs https://2ace.pl/**, https://www.2ace.pl/**Where confirmation and password links send people. A wrong value sends them to localhost.

When something looks wrong

SymptomLikely cause and fix
Confirmation email links open localhost.Supabase Auth Site URL is not set to https://2ace.pl.
Emails do not arrive.Resend key missing, or the sending domain is not verified.
Customer paid but plan is not active.The Stripe webhook is not reaching the server. Check the webhook endpoint and secret.
A plan change shows an "ACTION NEEDED" email.Stripe and our plan record disagree. Compare the customer's Plan card with the Stripe subscription, and fix the one that is wrong.
Receiving photos or the customer change buttons fail.The latest database migration or function deploy has not been run.
Shipping → Test connection says the login was refused.Check the Furgonetka email and password, that the Client ID and Secret belong to the same environment as FURGONETKA_ENV, and that the account has a password set (an account created with Google sign-in has none).
Packing finished but "No label created automatically".The packing is done; only the label step stopped, and the message says why (a limit, the balance, a carrier that refused). Open the order in the admin panel and use Get shipping prices to choose, or Create the cheapest label to try again. If the message says the carrier did not confirm, do not retry: use Check the label order.
A label order is "waiting to be checked".Furgonetka did not confirm the order in time, or recording it failed. It may already have been charged, so nobody should buy again. Open the order and press Check the label order: it asks Furgonetka what happened and either records the label or closes the attempt. You also get an email at the team address.
Buying a label says it is switched off or over a limit.Those are the settings SHIPPING_ENABLED, SHIPPING_MAX_LABEL_PLN and SHIPPING_DAILY_CAP_PLN. Each refusal says which one it is.
I cannot find a customer's Shipping and fulfilment settings.They are inside the customer's page: Customers, click the company's row, choose a reason, then scroll below the Plan box. The Shipping item in the left menu is only the Furgonetka connection test. Only admins see Edit. Hard-refresh if the box is missing.
A customer cannot add their own label.Check that their plan includes fulfilment (or an admin set the mode override), that the order is not shipped or cancelled, that the person is an owner, operations or staff member, and that the customer-shipping function is deployed.
The booking page says "not open yet".No meeting language is switched on. Open Appointments → Booking settings, tick Open for booking and give each language opening times and an email address.
Appointments says "Reminders are not running".The database job has not run in the last 30 minutes. Check that the migration ran (supabase db push --yes) and that the functions are deployed. In the Supabase dashboard, Database → Extensions must show pg_cron and pg_net enabled; enable them and run the push again. You can also call the booking-reminders function by hand; it only sends what is due.
A booked customer got no email.The booking is saved either way. Check RESEND_API_KEY and the verified sender, then use Resend confirmation on the booking.
Shipping says "Furgonetka answered 409: The carrier's regulations have changed".Furgonetka needs the account to accept updated carrier terms. Log in to the Furgonetka account the website uses (test: sandbox.furgonetka.pl/konto, live: furgonetka.pl/konto) and accept them. Do the same on the live account before the first live label. Nothing was charged.
"Furgonetka did not order it … error communicating with the carrier API".The carrier's system failed after Furgonetka accepted the shipment. Common in the test environment. Nothing was charged. Try again later or with another carrier. If every carrier fails the same way, check the shipment details on the order.
Download label says the file is still being prepared.Not an error. Furgonetka can take up to a minute to produce the PDF. Wait and click again.
Appointments says the booking tables are missing, or an order's "Edit details" or correction note does not work.The latest database update was not applied. Run supabase db push --yes (with SUPABASE_DB_PASSWORD set), then deploy admin-api and booking again.
"Ask the customer to correct it" says the email could not be sent.Check RESEND_API_KEY and the verified sender. The order shows no "asked" note until the email is accepted.
A customer on Fulfilment as you go sees only "buying is coming soon".Buying is closed until CUSTOMER_LABELS_ENABLED=true is set and May buy labels themselves is ticked for that customer, their plan is active, and the Furgonetka login works.
A customer says the price changed or a limit was reached.The price is asked again from the carrier at the moment of buying. The limits are the per-customer settings (labels per day, total not yet invoiced) and the customer limits above. Raise them for that customer or wait.
A customer-bought label shows "The parcel does not match the label".The packed parcel is bigger or heavier than declared. Weigh again, then Accept the parcel (an admin can add the carrier's extra charge to the customer).
Usage charges are not on the customer's invoice.Check, in order: USAGE_BILLING_ENABLED is true; the Stripe webhook has the three invoice events; the customer is marked Live (otherwise the fees are test); the invoice is the monthly subscription invoice (not an upgrade); and the customer has a Stripe customer id. The charges stay pending in the ledger and are picked up by the next monthly invoice.
A return label cannot be made ("could not price" or the carrier refuses).Furgonetka must accept a pickup from the buyer's address to our warehouse. Check the buyer's name (first name and surname) and phone on the return, and try another carrier. If no carrier works for private senders in the sandbox, tell the developer: the return form may need a drop-off point.
A handling fee shows "oversize" with 0.A packed parcel is bigger than the biggest tariff class. Set the charge by hand (an admin adds an adjustment) or add a bigger class under Shipping → Handling fee tariff.
A staff member cannot see a screen.Check their role. Admin and Support also need the two-step code.
Example

You add a new feature with Claude and it asks you to run the database step. You run supabase db push --yes, then deploy the functions it names, then tell it to "commit and push". After about a minute you hard-refresh the admin panel and the new screen is there.
